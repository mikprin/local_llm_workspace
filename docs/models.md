# Выбор моделей

Журнал фактических решений по моделям для этой машины (RTX 4070 Ti Super 16 ГБ).
Общая методология — квантование, формула VRAM, чтение `ollama ps` — в [../README.md](../README.md).
Здесь то, чего там нет: **как искать модели самому** и **какие цифры получились в итоге**.

Все числа ниже сняты с HuggingFace API, а не взяты по памяти. Это важно: модельный ряд
обновляется быстрее, чем любой источник успевает устареть, — включая знания LLM,
у которых есть дата отсечки. Поколения Qwen3.5/3.6/3.8 — наглядный пример.

## Итог: что стоит на машине

| Роль | Модель | Веса | VRAM | Скорость |
|---|---|---|---|---|
| **Повседневная** | `hf.co/unsloth/Qwen3.5-9B-GGUF:Q8_0` | 8.9 ГБ | 12.3 ГБ @32k | ~40–50 ток/с, 100% GPU |
| **Тяжёлая** | `hf.co/unsloth/Qwen3.8-27B-GGUF:UD-Q4_K_M` | 15.3 ГБ | 18.9 ГБ @16k | ~8–12 ток/с, ~25% в CPU |

Логика пары: 9B закрывает всё интерактивное, 27B достаётся под задачи,
где не жалко подождать. Держать только одну из них смысла нет —
они покрывают разные режимы работы.

Отдельно стоит отметить 9B: она влезает в **Q8_0**. Обычно на 16 ГБ приходится
жить на Q4 и мириться с потерями, а здесь квантование практически не влияет
на качество. Это лучше, чем 27B в агрессивном кванте, — см. «Развилку» ниже.

## Как искать модели

### Шаг 0. Убедиться, что модель существует

Не полагайтесь на память — ни на свою, ни на LLM:

```bash
curl -s "https://huggingface.co/api/models?author=Qwen&search=Qwen3&sort=downloads&direction=-1&limit=20" \
  | jq -r '.[].modelId'
```

### Шаг 1–2. Найти GGUF и собрать команду

Скрипт [scripts/find-gguf.sh](../scripts/find-gguf.sh) делает оба шага:

```bash
scripts/find-gguf.sh Qwen3.8-27B                              # какие есть GGUF-репозитории
scripts/find-gguf.sh Qwen3.8-27B unsloth/Qwen3.8-27B-GGUF     # кванты + готовые строки pull
```

Второй вызов сразу печатает команды с пометками ✅/⚠️/❌ по размеру относительно 16 ГБ.

То же самое мышкой: страница репозитория → вкладка **Files** (имена и размеры),
либо кнопка **Use this model → Ollama**, которая генерирует строку сама.

### Анатомия строки

```
ollama pull  hf.co/ unsloth/Qwen3.8-27B-GGUF : UD-Q4_K_M
             └─┬──┘ └───────────┬──────────┘   └───┬───┘
      префикс HF     modelId (owner/repo)         квант
```

Тег кванта = имя `.gguf`-файла без префикса с названием модели:
`Qwen3.8-27B-UD-Q4_K_M.gguf` → `UD-Q4_K_M`. Матчится регистронезависимо.

### Главная ловушка: safetensors против GGUF

**Официальный репозиторий модели Ollama не подойдёт.** `Qwen/Qwen3.8-27B` содержит
`.safetensors` — формат для PyTorch и vLLM. Ollama (llama.cpp) работает только с **GGUF**,
и качать надо конверт от сообщества.

Кому доверять: `unsloth`, `bartowski`, `ggml-org`, `lmstudio-community`.

Что пропускать, невзирая на большие счётчики скачиваний: всё с `Uncensored`,
`abliterated`, `OBLITERATED`, `Heretic`, `Cold-Fusion` в названии — это правки
поведения модели, а не просто конвертация формата.

### Чего API не даёт

Архитектурных чисел для расчёта KV-кеша. Их берут из `config.json` официального репозитория:

```bash
curl -s https://huggingface.co/Qwen/Qwen3.8-27B/raw/main/config.json | jq
```

Нужны `num_hidden_layers`, `num_key_value_heads`, `head_dim`. У новых Qwen они лежат
вложенно в `text_config` — модели мультимодальные, и на верхнем уровне их нет.

## Расчёт: почему выбрано именно это

```
байт/токен KV = 2 × слоёв × kv_heads × head_dim × байт_на_элемент
```

| | Qwen3.5-9B | Qwen3.8-27B |
|---|---|---|
| Слоёв | 32 | 64 |
| KV-голов (GQA) | 4 | 4 |
| head_dim | 256 | 256 |
| Максимальный контекст | 262144 | 262144 |
| KV при `q8_0` | 64 КБ/токен | 128 КБ/токен |

Отсюда через [scripts/vram.py](../scripts/vram.py):

```bash
scripts/vram.py 9  --quant q8_0   --ctx 32768 --layers 32 --kv-heads 4 --head-dim 256   # 12.3 ГБ ✅
scripts/vram.py 27 --quant q4_k_m --ctx 16384 --layers 64 --kv-heads 4 --head-dim 256   # 18.9 ГБ ❌
```

Не забудьте передать архитектурные флаги — дефолты в скрипте от другой модели
и дадут заниженный KV.

## Что рассматривалось и было отклонено

| Кандидат | Проблема |
|---|---|
| `Qwen3.8-27B:UD-Q4_K_XL` (16.4 ГБ) | offload больше половины |
| `Qwen3.6-27B:UD-Q4_K_XL` (16.4 ГБ) | то же, а поколение старее |
| `Qwen3.6-35B-A3B:UD-IQ4_XS` (16.5 ГБ) | MoE, offload переносит легко — **стоит попробовать** |
| `Qwen3.8-27B:UD-IQ3_S` (11.2 ГБ) | влезает целиком, но IQ3 заметно тупит |
| `Qwen3.5-9B:UD-Q4_K_XL` (5.6 ГБ) | смысла нет, когда Q8_0 помещается |

MoE `35B-A3B` — самый интересный неиспробованный вариант: 35B параметров при ~3B
активных на токен. Выгруженные эксперты вызываются редко, поэтому offload бьёт
по скорости куда слабее, чем у плотной модели. Может оказаться быстрее 27B при
большем размере.

## Развилка: 27B@Q4 против 9B@Q8

Правило «модель побольше в грубом квантовании бьёт модель поменьше в точном»
(см. README) верно **до Q4 включительно**. Ниже оно ломается, и здесь есть нюанс,
которого в правиле нет: **offload тоже стоит денег**.

- 27B@Q4 с 25% слоёв в RAM ≈ 8–12 ток/с
- 9B@Q8 целиком в VRAM ≈ 40–50 ток/с

Вчетверо медленнее ради выигрыша в качестве, который на многих задачах не заметен.
Проверяйте на своих задачах, а не по бенчмаркам:

```bash
docker exec ollama ollama ps    # сплит CPU/GPU — главная проверка
docker exec -it ollama ollama run <модель> --verbose   # eval rate в конце сессии
```

Если 27B ощущается слишком медленной, следующий шаг — `UD-IQ4_XS` (13.3 ГБ):
offload падает с 25% примерно до 10%, качество почти то же.

## Что происходит при нехватке VRAM

Ollama не падает, а раскладывает слои между GPU и RAM. Причина замедления — в пропускной способности:

| | ГБ/с |
|---|---|
| VRAM (RTX 4070 Ti Super) | ~670 |
| RAM (DDR4-3200, 2 канала) | ~50 |

На каждый токен читаются все веса, поэтому разница в 13 раз означает,
что слои в RAM определяют время целиком.

| Offload | Скорость 14B-класса |
|---|---|
| 0% | ~50 ток/с |
| 25% | ~15 ток/с |
| 50% | ~9 ток/с |

Три оговорки:

- **MoE переносят offload гораздо легче** — редко вызываемые эксперты.
- **Обработка промпта** упирается в вычисления, а не в память, и страдает меньше генерации.
- **CUDA OOM** — настоящий краш, а не замедление — случается, когда не влезает сам
  KV-кеш при заданном `OLLAMA_CONTEXT_LENGTH`. Лечится уменьшением контекста;
  это первое, что стоит крутить.

## Настройка контекста на модель

В `compose.yaml` стоит `OLLAMA_CONTEXT_LENGTH=32768` — это под 9B.
Для 27B столько много и лишь увеличит offload, но глобальную переменную
трогать не нужно, иначе урежете 9B без причины.

Контекст задаётся на конкретную модель в Open WebUI:
**Settings → Models → выбрать модель → Advanced Params → `num_ctx` = 16384**.

Через API — параметром запроса:

```bash
curl http://localhost:11434/api/generate -d '{
  "model": "hf.co/unsloth/Qwen3.8-27B-GGUF:UD-Q4_K_M",
  "prompt": "...",
  "options": {"num_ctx": 16384}
}'
```

## Мультимодальность

Обе модели — Vision-Language (`Qwen3_5ForConditionalGeneration`, в `config.json`
есть `vision_config`). В GGUF-репозиториях рядом лежит отдельный `mmproj-F16.gguf`
(~0.9 ГБ) — визуальный энкодер.

Ollama обычно подтягивает его сам. Учитывайте, что это ещё почти гигабайт VRAM
сверх расчётов выше, если собираетесь работать с картинками.
