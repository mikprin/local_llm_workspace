# Локальные LLM

Стек для локального запуска языковых моделей: браузерный чат + OpenAI-совместимый API,
доступные в локальной сети. Всё в Docker — ради воспроизводимости.

## Железо

| | |
|---|---|
| GPU | NVIDIA RTX 4070 Ti Super, 16 ГБ VRAM (драйвер 580.173, CUDA 13.0) |
| CPU | AMD Ryzen 7 5800X, 8 ядер / 16 потоков |
| RAM | 31 ГБ |
| Диск | `/mnt/pop_os` — 116 ГБ свободно |
| LAN | `10.12.12.148/24` (`enp9s0`) |

16 ГБ VRAM — ключевое ограничение: оно определяет выбор моделей и движка.

## Почему Docker

Потери производительности на GPU-инференсе практически нет — единицы процентов, в пределах
шума. Контейнер работает с хостовым драйвером напрямую, без прослойки виртуализации.
Взамен получаем воспроизводимость, изоляцию версий CUDA и простой откат.

Единственное требование — **NVIDIA Container Toolkit**. Без него флаг `--gpus` не работает.

## Установка

### 1. NVIDIA Container Toolkit (нужен sudo, один раз)

```bash
curl -fsSL https://nvidia.github.io/libnvidia-container/gpgkey \
  | sudo gpg --dearmor -o /usr/share/keyrings/nvidia-container-toolkit-keyring.gpg
curl -s -L https://nvidia.github.io/libnvidia-container/stable/deb/nvidia-container-toolkit.list \
  | sed 's#deb https://#deb [signed-by=/usr/share/keyrings/nvidia-container-toolkit-keyring.gpg] https://#g' \
  | sudo tee /etc/apt/sources.list.d/nvidia-container-toolkit.list
sudo apt update && sudo apt install -y nvidia-container-toolkit
sudo nvidia-ctk runtime configure --runtime=docker
sudo systemctl restart docker
```

Проверка — команда должна напечатать таблицу `nvidia-smi` изнутри контейнера:

```bash
docker run --rm --gpus all nvidia/cuda:12.6.0-base-ubuntu24.04 nvidia-smi
```

### 2. Запуск стека

```bash
cd ollama-stack
docker compose up -d
docker compose exec ollama ollama pull qwen2.5-coder:14b
```

```bash
docker compose exec ollama ollama --version   # версия сервера внутри
docker compose exec ollama ls /root/.ollama/models/blobs   # сами gguf-файлы
docker compose exec ollama nvidia-smi         # контейнер видит GPU хоста
curl http://localhost:11434/api/tags          # что установлено, без CLI
```


### 3. Доступ

| Что | Локально | Из локальной сети |
|---|---|---|
| Браузерный чат (Open WebUI) | http://localhost:3000 | http://10.12.12.148:3000 |
| API Ollama (OpenAI-совместимый) | http://localhost:11434/v1 | http://10.12.12.148:11434/v1 |

Ключ API для сырого Ollama не проверяется — подойдёт любая непустая строка.

## Выбор движка

| | **Ollama** (llama.cpp) | **vLLM** |
|---|---|---|
| Старт | из коробки | нужно подбирать флаги |
| Модели больше VRAM | да, offload на CPU | нет, только целиком в VRAM |
| Скорость одного запроса | хорошая | чуть выше |
| Параллельные запросы | посредственно | в разы быстрее (PagedAttention) |
| Формат весов | GGUF-кванты | AWQ / GPTQ / FP8 |

При 16 ГБ VRAM начинаем с **Ollama**: он переживает модели, не влезающие в видеопамять
целиком. К vLLM имеет смысл вернуться, когда появятся батчи или несколько агентов,
работающих параллельно.

## Модели под 16 ГБ (квантование Q4_K_M)

| Модель | ~VRAM | Для чего |
|---|---|---|
| `qwen2.5-coder:14b` | ~9 ГБ | базовый кодинг, остаётся много места под контекст |
| `gpt-oss:20b` | ~13 ГБ | хороший tool-calling, годится для агентов |
| `devstral:24b` | ~14 ГБ | заточен под агентные правки кода, но контекст поджимает |
| `qwen3-coder:30b-a3b` | ~18 ГБ | MoE: целиком не влезает, но активны лишь ~3B — с частичным CPU-offload работает бодро |

Модельный ряд меняется быстро — перед выбором стоит свериться с актуальным
[ollama.com/library](https://ollama.com/library).

## Как выбирать модель

Выбор сводится к трём вопросам: что скачать, в каком квантовании и влезет ли оно в VRAM.

### Анатомия имени

```
qwen2.5-coder : 14b - instruct - q4_K_M
└─ семейство ─┘  └─┬─┘  └──┬───┘  └──┬──┘
                размер   вариант   квантование
```

- **Семейство** — кто обучал и на чём (`coder` = дообучена на коде)
- **Размер** — миллиарды параметров; главный рычаг качества и главный пожиратель VRAM
- **Вариант** — `instruct` (умеет вести диалог, нужен почти всегда) против `base` (только продолжает текст)
- **Квантование** — во сколько бит ужат каждый вес

Если указать просто `qwen2.5-coder:14b`, подставится дефолтный тег — обычно `q4_K_M`.
Явное квантование нужно, когда осознанно хотите другое соотношение качества и размера.

### Квантование

| Тег | бит/вес | Что происходит |
|---|---|---|
| `q8_0` | 8 | практически неотличимо от оригинала, но вдвое тяжелее |
| `q6_K` | ~6.6 | потери на уровне погрешности |
| `q5_K_M` | ~5.7 | хороший компромисс, если место есть |
| **`q4_K_M`** | ~4.8 | **рабочий дефолт** — ниже начинается заметная деградация |
| `q3_K_M` | ~3.9 | уже чувствуется: модель тупит на длинных цепочках рассуждений |
| `q2_K` | ~3.0 | обычно бессмысленно |

**Правило, которое почти всегда верно:** модель побольше в грубом квантовании бьёт модель
поменьше в точном. 14B@Q4 лучше, чем 7B@Q8, при одинаковом весе. А вот опускаться ниже Q4
ради экономии места — плохая сделка: там эта логика ломается.

### Прикидка VRAM

```
вес модели ≈ (млрд параметров) × (бит на вес) / 8   ГБ
```

Пример: `14 × 4.8 / 8 ≈ 8.4 ГБ` — сходится с таблицей выше.

Но в 16 ГБ помещается не только модель:

| Статья расхода | Сколько |
|---|---|
| Всего VRAM | 16.0 ГБ |
| − рабочий стол, GNOME, Firefox | 0.6–2 ГБ (**плавает** в зависимости от нагрузки на браузер) |
| − KV-кеш (контекст) | 1–3 ГБ на 32k при сжатии `q8_0` |
| − буферы вычислений | ~0.5 ГБ |
| **= остаётся на веса** | **примерно 11–13 ГБ** |

Практический ориентир: **веса до ~12 ГБ — комфортно; 13–14 ГБ — впритык и зависит
от того, открыт ли браузер.**

KV-кеш растёт линейно от длины контекста: модель, влезающая на 8k, может не влезть на 32k.
Именно поэтому в конфиге стоит `OLLAMA_KV_CACHE_TYPE=q8_0` — это режет кеш примерно вдвое.

### Проверка результата

Ollama никогда не падает от нехватки VRAM — он молча выгружает часть слоёв на CPU,
и скорость проваливается в разы. Единственный способ узнать правду:

```bash
docker compose exec ollama ollama ps
```

```
NAME                 SIZE     PROCESSOR
qwen2.5-coder:14b    10 GB    100% GPU        ← то, что нужно
devstral:24b         16 GB    82%/18% CPU     ← часть на CPU, будет медленно
```

Цель — строка `100% GPU`. Всё, где появился CPU, стоит заменить на квантование поменьше.

Исключение — **MoE-модели** (`qwen3-coder:30b-a3b`): из 30B параметров активны лишь ~3B
на токен, поэтому частичный offload переносится нормально. Для плотных моделей это
приговор скорости.

### Модели помимо каталога

Кроме `ollama.com/library` можно тянуть любой GGUF прямо с HuggingFace — это даёт точный
контроль над квантованием и доступ к тому, чего нет в официальном каталоге:

```bash
ollama pull hf.co/bartowski/Qwen2.5-Coder-14B-Instruct-GGUF:Q5_K_M
```

### Порядок действий

1. Взять максимальный размер, чей вес по формуле укладывается в ~12 ГБ
2. Квантование `q4_K_M`; если не влезает — **уменьшать размер модели, а не квантование** ниже Q4
3. Скачать, запустить, посмотреть `ollama ps`
4. Не `100% GPU` — либо квант ниже, либо контекст короче, либо модель меньше

## Агентный кодинг

Claude Code формально можно перенаправить на локальный эндпоинт через `ANTHROPIC_BASE_URL`,
но модели на 14–30B на его агентном цикле спотыкаются. Лучше работают инструменты,
изначально рассчитанные на модели поскромнее:

- **Cline / Roo Code** (VS Code) — провайдер «OpenAI Compatible», URL `http://10.12.12.148:11434/v1`
- **Continue.dev** — лучший вариант для inline-автодополнения
- **aider**:
  ```bash
  aider --model openai/qwen2.5-coder:14b --openai-api-base http://10.12.12.148:11434/v1
  ```

Практический расклад: локальная модель — для автодополнения, рефакторинга и работы
с приватным кодом; сложные многошаговые задачи пока честнее оставлять облачной.
Разрыв в агентных способностях большой.

## Безопасность

Порты открыты на `0.0.0.0` — сервисы видны всей локальной сети.

**Open WebUI** защищён: `WEBUI_AUTH=True`, вход по учётной записи (первый
зарегистрировавшийся становится администратором — заведите аккаунт сразу после запуска).

**У Ollama аутентификации нет вообще.** Любой в `10.12.12.0/24` может не только
генерировать текст, но и заливать и удалять модели через тот же API. Если сеть
не полностью доверенная, выберите один из вариантов.

### Вариант А — не публиковать сырой порт

Open WebUI сам отдаёт OpenAI-совместимый API с ключами, которые выдаются
в настройках профиля:

```
http://10.12.12.148:3000/api      # заголовок: Authorization: Bearer <ключ из UI>
```

Тогда в `compose.yaml` достаточно закомментировать строку `- "0.0.0.0:11434:11434"` —
сервисы всё равно общаются между собой по внутренней сети Compose.

### Вариант Б — ограничить файрволом

Ловушка: **ufw не действует на опубликованные Docker-порты** — Docker добавляет свои
правила в цепочку `DOCKER` раньше, чем отрабатывает ufw. Фильтровать нужно
через `DOCKER-USER`:

```bash
sudo iptables -I DOCKER-USER -p tcp --dport 11434 ! -s 10.12.12.0/24 -j DROP
```

Правило не переживёт перезагрузку — сохраните его через `iptables-persistent`.

## Настройки в compose.yaml

| Переменная | Зачем |
|---|---|
| `OLLAMA_KEEP_ALIVE=30m` | держать модель в VRAM между запросами, не перезагружать |
| `OLLAMA_FLASH_ATTENTION=1` | быстрее и экономнее по памяти на длинном контексте |
| `OLLAMA_KV_CACHE_TYPE=q8_0` | сжатие KV-кеша — заметная экономия VRAM |
| `OLLAMA_CONTEXT_LENGTH=32768` | размер контекста по умолчанию |
| `OLLAMA_HOST=0.0.0.0:11434` | слушать все интерфейсы, а не только loopback |
| `OLLAMA_ORIGINS=*` | без этого браузерные клиенты упрутся в CORS |

Модели и история чатов лежат в именованных томах Docker (`ollama-models`, `open-webui`)
и переживают пересоздание контейнеров.

## Полезные команды

```bash
docker compose logs -f ollama              # логи
docker compose exec ollama ollama list     # список загруженных моделей
docker compose exec ollama ollama ps       # что сейчас в VRAM
docker compose exec ollama ollama pull <модель>
docker compose exec ollama ollama rm <модель>
nvidia-smi -l 1                            # мониторинг VRAM в реальном времени
docker compose pull && docker compose up -d   # обновление образов
```
